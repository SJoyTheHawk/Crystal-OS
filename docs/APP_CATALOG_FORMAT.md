# Crystal online app catalog

The online catalog is a signed JSON document and a set of already-built `.capp`
files served from HTTPS hosting. It is not generated by a build server and is
not embedded in firmware. Publishing a new catalog or app package does not
require an OTA update; the computer-side catalog client fetches the current
listing and selected package from their HTTPS URLs before transferring the
package to the device.

The project hosting URL is not assigned yet. Keep it configurable until a
project-controlled host and release key are selected. Do not put a private
signing key in this repository, firmware, or a public web host.

## Source payload

The curator maintains a JSON payload with this shape:

```json
{
  "schema": 1,
  "generated": "2026-11-11T00:00:00Z",
  "apps": [
    {
      "id": "org.crystal.example",
      "name": "Example",
      "version": "1.0.0",
      "min_os": "1.0.0",
      "abi": 1,
      "package_key_id": 12,
      "description": "A short description shown in the catalog.",
      "package_url": "https://apps.example.org/org.crystal.example-1.0.0.capp",
      "sha256": "<64 lowercase hexadecimal characters>",
      "size": 12345
    }
  ]
}
```

Each package is built and signed separately. `sha256` and `size` cover the exact
downloaded `.capp` bytes, including its signature trailer. The package
signature is independently verified against the configured package trust
store after download.

## Signed document

The published `catalog.json` wraps the payload in an envelope:

```json
{
  "catalog": { "schema": 1, "generated": "...", "apps": [] },
  "key_id": 7,
  "signature": "<base64 Ed25519 signature>"
}
```

The signature covers the UTF-8 encoding of the `catalog` object serialized as
JSON with sorted keys, no insignificant whitespace, ASCII escaping, and no
NaN values. This gives publishers and clients one canonical byte sequence.
The envelope's key ID selects a catalog Ed25519 public key. Each app's
`package_key_id` separately selects the public key used for its `.capp` trailer.
These may be different keys, so catalog publishing can be delegated separately
from app signing. Unknown keys, invalid signatures, non-HTTPS package URLs,
duplicate app IDs, unsupported schema/ABI, and invalid package metadata are
rejected.

## Curating and publishing

1. Build and Ed25519-sign each app package with `crystal pack`.
2. Upload the immutable `.capp` files to HTTPS hosting. Record each final URL,
   SHA-256, and byte size in the source payload.
3. Sign the payload locally with the catalog release key:

   ```sh
   ./tools/crystal catalog-sign catalog-source.json \
     --key /secure/path/catalog-release.pem --key-id 7 \
     --output public/catalog.json
   ```

4. Upload `catalog.json` last, after all referenced packages are available.
   The web host only serves files; it does not build apps.

The CLI can fetch and verify the live listing, or download a selected app and
verify the catalog signature, package hash, package signature, app ID, and
version:

```sh
./tools/crystal catalog https://apps.example.org/catalog.json \
  --trusted-key 7=/secure/path/catalog-public.pem

./tools/crystal catalog-download https://apps.example.org/catalog.json \
  org.crystal.example -o ./org.crystal.example.capp \
  --trusted-catalog-key 7=/secure/path/catalog-public.pem \
  --trusted-package-key 12=/secure/path/package-release-public.pem
```

Catalog and package trust keys are configured separately. The catalog URL is a
deployment setting and remains unset until the project chooses its hosting
domain.

This document describes the catalog format and host-side curation workflow.
Phase 15 firmware verifies signed packages against configured trusted keys,
but does not yet browse or download the online catalog on the device. Configure
the release public key before signed packages can be admitted on a device.
